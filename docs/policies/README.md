# Permanent Sthira policies

These documents preserve the decisions that should survive individual implementations and reviews. They state required behavior and how to verify it; they do not certify that the current application has passed every check.

| Policy | Authority |
|---|---|
| [Product contract](product.md) | User experience, knowledge ownership, provenance, navigation, and data safety. |
| [Design and interaction](design.md) | Visual language, page composition, alignment, graphics, accessibility, and tone. |
| [Verification and evidence](verification.md) | Functional coverage, isolated fixtures, fresh visual checks, honest results, and temporary evidence retention. |

Latest explicit owner decisions come first, followed by these policies. [Product understanding](../sthira_product_understanding.md) and the [detailed design system](../design/sthira-design-system-v1.md) provide supporting context. Historical implementation plans describe earlier work and must not override these policies. Actual code establishes what exists, not automatically what is correct.

The five [approved design references](../design/README.md) remain stable visual targets. Mockup copy, sample entities, old controls, and decorative graph links are illustrative; never insert them as real workspace facts.

Keep policies in place and update the relevant section when an owner decision changes. Avoid competing copies of the same rule. Keep current [known limitations](../known-limitations.md) separate from permanent requirements. Generated screenshots, logs, audit summaries, and QA databases belong in ignored temporary output, not this policy directory.
